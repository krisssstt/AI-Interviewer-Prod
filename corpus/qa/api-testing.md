# Проверка API: контракт, доступ и повторы

Авторский учебный материал проекта, редакция 1. Справочная основа: RFC 9110 и спецификация OpenAPI. Проверки следует согласовывать с опубликованным контрактом конкретной системы.

## Контракт и бизнес-инварианты

Проверка API включает HTTP-метод, путь, параметры, заголовки, статус и структуру тела. Схема определяет типы, обязательность и допустимые значения, но не все бизнес-правила. Например, JSON с корректными полями может содержать неверную сумму заказа. Поэтому дополнительно проверяют связи между значениями, бизнес-инварианты, изменение состояния и побочные эффекты.

Для создания заказа полезен сценарий: отправить корректный запрос, проверить статус по контракту и идентификатор; прочитать созданный заказ; сравнить владельца, позиции и сумму; убедиться, что второй заказ не появился. Негативные случаи должны проверять ожидаемый отказ, понятный код ошибки и отсутствие частично сохранённых некорректных данных. Быстрый ответ с неверным результатом не является успехом.

## Разграничение доступа к объектам

Аутентификация устанавливает личность, авторизация разрешает действие над конкретным объектом. Наличие действительной сессии не означает право читать любой заказ. Для проверки нужны два пользователя и реальные разные объекты: пользователь A пытается прочитать, изменить и удалить объект пользователя B, подставляя его идентификатор в прямой HTTP-запрос.

Ожидаются предусмотренный политикой 403 либо 404, отсутствие чужих данных в ответе и отсутствие изменения объекта. Проверку выполняют для каждого метода и вложенного ресурса, включая экспорт и поиск. Скрытие кнопки, readonly-поле и проверка только в JavaScript не обеспечивают серверный контроль доступа. Административная роль также не должна случайно давать доступ к частным документам вне принятой политики.

## Повторы и ключ идемпотентности

После таймаута клиент не знает, был ли создан платёж. Прикладной ключ идемпотентности позволяет повторить запрос без второго эффекта. Сервер должен связывать ключ с пользователем, операцией и исходными параметрами, а не доверять факту наличия строки в заголовке.

Проверки: одинаковые ключ и параметры дают один побочный эффект и согласованный результат; тот же ключ с другим телом отклоняется как конфликт; одинаковые ключи разных пользователей не раскрывают результаты друг друга; конкурентные запросы не создают дубликаты. Отдельно проверяют поведение до завершения первого запроса, после рестарта и по истечении срока хранения ключа. Новый ключ означает новый запрос, поэтому автоматическое создание нового ключа при каждом retry может нарушить защиту.

## Разбор ошибок

Фиксируйте минимальный воспроизводимый запрос, предусловия и ответ. Не включайте секретные токены и чужие данные в общие журналы. Если операция отклонена, проверьте не только сообщение, но и транзакционный результат. Отрицательный тест успешен, когда система корректно отказала, а не когда тест получил любой ошибочный статус.
